## 1. 直接结论

建议本项目 V1 采用“前后端分离的模块化单体”，不要直接改造 Open edX、Moodle、Canvas，也不要整套套用 Dify 或 RAGFlow。

候选基线如下：

| 层级 | 推荐候选 | 当前结论 |
|---|---|---|
| 架构 | 前后端分离 + 模块化单体 + 独立异步任务进程 | 推荐 |
| 后端 | Python 3.12 + FastAPI + Pydantic | 推荐 |
| 前端 | React + TypeScript + Vite | 推荐 |
| 关系与向量数据 | PostgreSQL + pgvector | 推荐作为 V1 起点 |
| 数据访问与迁移 | SQLAlchemy 2 + Alembic | 推荐；尚未授权创建 Schema 或迁移 |
| 异步任务 | Celery + Redis | 推荐用于导入、解析、索引和重试 |
| 原始文件 | S3 兼容对象存储适配层；本地开发实现与生产实现分离 | 候选，待文件规模确认 |
| 文档解析 | Docling 为主，按文件类型保留专用解析器与 OCR 降级路径 | 候选，待数据测试 |

## 2. 调研范围与判断方法

共对比 9 个项目：

- 教育/LMS：Open edX、Moodle、Canvas LMS。
- 知识库/RAG：Dify、RAGFlow、MaxKB、AnythingLLM、Open WebUI、FastGPT。

选择标准：与课程内容、文档导入、知识检索、题库、对话、引用、运营管理或 RAG 工程至少一项高度相关；技术事实必须能由官方仓库或官方文档复核。

本次没有访问数据目录。因此，文档解析效果、中文召回、题目结构识别、并发、延迟、资源预算和模型选择只能给出候选，不能标记为 `passed`。

### 3.1 教育项目给出的结论

Open edX 的官方文档显示其大部分后端采用 Django、前端采用 React 微前端，且课程创作与学习交付分成 CMS/LMS；这支持将“教学运营端”和“学员/助教端”明确分离，但不代表本项目要复制其微服务规模。[Open edX Platform Overview](https://docs.openedx.org/en/latest/developers/concepts/platform_overview.html)

Moodle 与 Canvas 的价值主要在业务模型：课程、内容、角色、管理和扩展边界成熟。它们分别以 PHP 和 Ruby 为核心，不适合作为当前 Python AI 知识库的直接基座。[Moodle README](https://github.com/moodle/moodle/blob/main/README.md)、[Canvas LMS](https://github.com/instructure/canvas-lms)

### 3.2 RAG 项目给出的结论

MaxKB 官方列出的组合是 Vue + Django + LangChain + PostgreSQL/pgvector，说明小到中等规模的知识库可以先用关系库与向量扩展统一承载。[MaxKB README](https://github.com/1Panel-dev/MaxKB)

Open WebUI 采用 SvelteKit + FastAPI，其官方 RAG 文档明确指出默认 ChromaDB 不适合多 worker，并建议规模化时改为 PGVector。这支持本项目不以本地嵌入式向量库作为正式 V1 基线。[Open WebUI Development](https://github.com/open-webui/docs/blob/main/docs/getting-started/advanced-topics/development.md)、[Open WebUI Essentials](https://github.com/open-webui/docs/blob/main/docs/getting-started/essentials.mdx)

RAGFlow 使用 Python + React，并组合 MySQL、Elasticsearch/Infinity、Redis、MinIO，代表功能强但运维重的路线。本项目可借鉴解析、检索和对象存储边界，但不应在未知数据规模时一次性引入全部服务。[RAGFlow 架构说明](https://github.com/infiniflow/ragflow/blob/main/AGENTS.md)、[RAGFlow Docker README](https://github.com/infiniflow/ragflow/blob/main/docker/README.md)

Dify 使用前后端分离、PostgreSQL、Redis/Celery 和可替换向量库，适合作为异步任务与 provider adapter 的参考；其许可证对多租户服务和前端标识有附加条件，因此建议只借鉴，不直接复制代码。[Dify API README](https://github.com/langgenius/dify/blob/main/api/README.md)、[Dify License](https://github.com/langgenius/dify/blob/main/LICENSE)

FastGPT 把 MongoDB 与向量数据库分开，并说明 pgvector 适合较轻量的索引规模、Milvus 面向更大的向量量级。这支持本项目采用“pgvector 起步，压测触发独立向量库”的路线，而不是现在预装 Milvus。[FastGPT Docker 部署](https://doc.fastgpt.cn/en/self-host/deploy/docker)

## 4. 推荐架构

```text
React + TypeScript Web
        │ REST + SSE
        ▼
FastAPI 模块化单体
  ├─ 课程与章节域
  ├─ 文档与来源域
  ├─ 题库与题目域
  ├─ 导入任务域
  ├─ 检索与问答域
  └─ 会话与历史域
        │
        ├─ PostgreSQL + pgvector
        ├─ Redis + Celery Worker
        ├─ S3-compatible Object Storage Adapter
        └─ Model Provider Adapter
              ├─ Embedding
              ├─ Reranker
              └─ LLM
```

### 4.1 为什么选择模块化单体

- 当前核心域数量有限，微服务会过早引入部署、链路追踪、接口版本和分布式一致性成本。
- 模块化单体仍可把课程、题库、文档、问答、任务和会话分层，满足需求中的可扩展性。
- 异步导入单独运行 worker，可隔离单个任务失败，无需先拆成多个网络服务。
- 当真实负载证明某一模块需要独立扩缩容时，再按指标拆分。

### 4.2 为什么选择 FastAPI

FastAPI 官方提供 OpenAPI/JSON Schema、流式响应、WebSocket 和测试客户端，能覆盖前后端契约、流式回答和接口测试。[FastAPI Features](https://fastapi.tiangolo.com/features/)

Python 也能直接连接 Docling、Embedding、Reranker 和 LangGraph，避免为 AI 流程增加跨语言服务。

### 4.3 为什么选择 React + TypeScript + Vite

- Open edX 与 RAGFlow 都使用 React 体系，AnythingLLM 采用 React/Vite；课程结构、导入进度、题目详情、引用卡片和流式聊天都有成熟的组件模式。
- V1 不需要 Next.js 的服务端渲染和全栈路由能力；Vite 更适合独立前端和清晰 API 边界。
- TypeScript 可将接口契约、流式事件和任务状态变成可检查类型。

### 4.4 为什么选择 PostgreSQL + pgvector

pgvector 官方支持精确与近似向量检索、HNSW/IVFFlat，并可与 PostgreSQL 全文检索组合。[pgvector README](https://github.com/pgvector/pgvector)

本项目大量依赖课程、项目、章节、题库、题目和来源之间的结构化关联。统一存放关系数据、向量和过滤字段，可以减少跨数据库一致性问题。中文关键词检索方案仍需在数据测试阶段验证，当前不假定 PostgreSQL 默认分词已经足够。

升级到 Milvus、Elasticsearch/OpenSearch 或其他独立检索服务的触发条件应是：向量规模、混合检索质量、过滤召回、并发或 P95 延迟经过压测不达标，而不是“其他项目用了”。

### 4.5 导入、解析与存储

- Celery + Redis：用于文件解析、内容切分、Embedding、索引和可重试任务。Celery 官方支持 Redis 作为 broker 和结果后端。[Celery Redis 文档](https://docs.celeryq.dev/en/v5.6.2/getting-started/backends-and-brokers/redis.html)
- Docling：支持 PDF、DOCX、PPTX、XLSX、HTML 和 Markdown 等统一表示，适合作为课程讲义和项目资料的首选解析候选。[Docling 支持格式](https://github.com/docling-project/docling/blob/main/docs/usage/supported_formats.md)
- 对象存储：原文件与派生文件通过统一适配层管理，数据库只保留业务元数据、状态和来源标识。是否直接引入 MinIO，需等部署环境与文件规模确认。

### 4.6 RAG 与对话编排

- 候选检索链：元数据约束 → 关键词/向量并行召回 → 合并去重 → Reranker → 证据门禁 → 回答与引用。
- BGE-M3 官方模型卡支持多语言以及 dense、sparse、multi-vector，并建议混合检索加重排，适合作为中文教育内容的首选候选。[BGE-M3 Model Card](https://huggingface.co/BAAI/bge-m3)
- LangGraph 官方文档提供 checkpoint 持久化和流式输出，适合多轮上下文、人工确认、恢复和可追踪状态；确定性的课程/题库 CRUD 不应放进图流程。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[LangGraph Streaming](https://docs.langchain.com/oss/python/langgraph/streaming)
- 大模型、Embedding 和 Reranker 都通过 provider adapter 接入；具体模型必须由中文课程问答黄金集决定。

### 前后端实施顺序建议

技术栈获批后，建议先定共享契约和后端最小纵向切片，再实现对应前端，而不是把整个后端写完才开始前端：

1. 冻结状态、错误、分页、引用和流式事件契约。
2. 后端先完成课程查询、导入任务状态和文档检索的最小接口骨架。
3. 前端同步实现课程列表、导入状态与引用展示。
4. 每个纵向切片执行契约测试和端到端验收。
5. 再扩展题库、多轮问答和历史记录。

这只是实施顺序建议，不是编码授权。
